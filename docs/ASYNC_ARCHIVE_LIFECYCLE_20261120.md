# OneSpace — immediate relationship transitions + asynchronous archives

Approved product direction: **Two of Us. One Space**. QA first. Production untouched until independent acceptance.

## Contract (the requested experience)

1. **Leave / remove / close:** the active relationship is ended or detached in the user's response transaction, not after an archive download or a restore operation. Existing old shared records are frozen, invisible to future partners and available ONLY to the original eligible recipients through authorized export infrastructure. No new pair may inherit old shared data.
2. **Atomic source preservation before the response:** take a durable, immutable, membership-scoped snapshot (not just a count, hash or pending row), or fail the action without detaching anyone. Preserve all eligible structured/written records including dependent history, with media, file pointers, photos, audio, videos and documents excluded. This is a technical dependency, not a user-facing archive wait.
3. **Separate recipient jobs:** one private and one original-pair shared archive per original member. Progress stage includes: queued -> source inventory (records identified) -> immutable snapshot verified -> records packaged (accurate numerator) -> encrypted -> ciphertext readback and digest validated -> available for 30 days -> user external save verified / TTL expiry -> purged. All values are server recorded and owner-scoped. Failed and retried jobs must be idempotent, bounded and resume from checkpoints. No invented percentages.
4. **After detachment:** original space tombstone must be preserved and never silently converted into a new couple's home. The previous shared space is **not** reused with a replacement partner. Existing requests and their archive progress must remain accessible to the original account even after membership is revoked.
5. **Delivery:** email to the verified email address of each recipient only after BOTH encryption and storage integrity checks pass. Use branded OneSpace from-domain. Email contains no data, raw storage path, ciphertext key or service token. Use an authenticated, revocable per-recipient link to **My Archives**. A normal Storage signed URL cannot be individually revoked, so use the authenticated download proxy with database status checks.
6. **Local copy:** on Android, the installed app may perform a user-authorized MediaStore Downloads save and hash readback, as supported by the existing bridge. The server cannot write to arbitrary phone Files storage while the app is not running. iOS requires a user-authorized document export. Browser downloads do not prove durable save; only a verified native save or a supported explicit proof/acknowledgement may trigger early purge.
7. **Retention:** make files unavailable as soon as a recipient's external save is proved, else at 30 days after issuance. Remove temporary encrypted Storage objects via janitor and retain audit metadata only as legally required. The email must state the expiry time accurately. Do not delete original source prematurely if any required snapshot or archive validation failed.
8. **Delete account:** user initiates a seven-day grace period, and export begins during it. On cancel, atomically cancel the deletion and every related outstanding archive job, revoke all download capabilities, purge unfinished temporary objects, and leave original account/space membership untouched. If a job already reached a verified external save, its **device copy is under user's control and cannot be remotely erased**; server artifacts can still be invalidated.
9. **Privacy:** private source rows appear only in that person's archive. The original pair's shared history appears as *read-only reference* in each original recipient's archive; it is never restored into a new couple's active shared tables. An archive can never give one partner the other's private content.
10. **Failure and retries:** a client may see "relationship ended — archive preparation requires attention." It must not silently present a pending action as completed or archive records as issued when the worker has only performed census. Preserve support and retry path until recovery.

## Technical engineering gates

- **A. Source-of-truth boundary**: enumerate and securely snapshot **all 69 classified families** using recipient-specific authorization, exclusions, validated dependent ownership, provenance and schema drift guards. The 23-family private mirror and census hashes alone do not meet this gate.
- **B. Portable encryption**: user-recoverable encrypted file envelope, integrity checks, tested key management and valid archives for **zero** records. Server-only encryption with an unrecoverable deleted key does not count. Build/verify chunked or ranged export with resumable continuation; remove 5,000-record/8-MiB prototype limitations.
- **C. Worker**: durable queued leases, retries, dead-letter handling, idempotent file issuance, per-recipient progress and cancellation; do not rely solely on an Edge Function instance remaining alive across deployment or timeouts.
- **D. Transition**: one atomic DB operation that snapshots origin references and detaches participants/marks original space closed while preventing old data exposure to newly paired users; never delete original source rows before durable snapshot.
- **E. Delivery**: verified address, branded provider acceptance and bounce handling, revocable authenticated link, **30 days** TTL or earlier verified external download, OS-level verified file save and independent ciphertext readback.
- **F. Account grace**: 7-day cancellation and purge scheduler gate tied to exporter state, including safe undo and concurrent worker cancellation.
- **G. QA acceptance**: original two empty QA spaces, synthetic heavy dataset, overlapping private/shared dependent history, large payloads, failed email, failed download, app offline, retries, cancellation at each boundary, RLS attempts from previous/new partners, QA/Production isolation, actual Android/iOS file saves.
